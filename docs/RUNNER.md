# Unattended runner architecture

A single persistent coordinator polls trusted local checker argv. Nonzero checks become jobs deduplicated by check ID, exact source baseline and HEAD. Pending findings are superseded before dispatch when HEAD/content changes; trusted discovery rechecks the new baseline before spending an AI call. Public task text cannot create commands or expand permissions. SQLite stores immutable configuration, spent/reserved budgets, job attempts/phases, stop signal and event history. A file lock excludes a second coordinator. Stop persists across restart; resume is explicit. Wall time includes downtime. Calls, maximum call duration, log bytes and attempt counts are reserved before process launch.

Each attempt uses an independent Git clone, a physically copied frozen workflow controller and a generated jobctl. The actual Codex worker directly claims, records progress and submits candidate through that CLI. It may edit only allowlisted core source/docs. The coordinator compares paths and frozen artifacts, preserves failed baseline checks, executes trusted tests and launches a separate read-only Codex reviewer in another independent clone. Machine evidence binds candidate content; reviewer verdict must bind the same digest. Worker assertions never accept a task. Failed candidates are retained and the next attempt starts from a clean baseline.

A separate guardian drains bounded output and kills a child process group on timeout or parent pipe EOF. This protects the backend/test processes supervised by this runner, not arbitrary subprocesses outside it. Each process reservation and PID/result location is durable. Recovery waits for guardians to finish before retry; attempts are charged even if a coordinator crashes.

An optional top-level `timeouts` object accepts `startup_seconds`, `idle_seconds` and `max_progress_extensions` (integer 0–3). Startup/idle values must be positive integers no greater than `budget.call_seconds`. Without this object, the original single-total timeout remains unchanged. With it, worker startup requires an active fenced Core claim; reviewer startup means only successful local process spawn, not an authenticated provider connection. Only coordinator-validated Core lifecycle checkpoints may renew idle: exact-baseline verification start, its machine-recorded failure, then submission of a different exact candidate. Stages and Core event sequence advance once in order; ordinary progress notes, heartbeats, tokens and stdout never renew idle. Every deadline is capped by the original call and runtime wall deadline, including downtime.

Guardian terminal results bind call ID, child/group PID, guardian PID and start time to their durable PID record, and explicitly confirm that the ordinary process group is gone. Missing, malformed or unconfirmed terminal receipts block recovery and prohibit rollback, restore and redispatch; expiration of a reservation alone is insufficient. Persistent stop permits recording already completed process facts but performs no integration or redispatch. These are cooperative same-user checks, not hostile-process isolation. A killed guardian or an escaped session can require manual intervention.

The precise top-level `failed to initialize in-process app-server client:
Operation not permitted (os error 1)` startup error is classified as
`infrastructure_blocked` before a model session. Admission requires a failed,
untruncated terminal output containing the exact error and only the known native
startup diagnostics. Successful exec, timeouts, generic operating-system errors,
unknown diagnostics and quoted or post-session task/tool output do not establish
this cause. The child records and returns its typed result before the owner
Supervisor durably stops further launches; no reserved session is refunded.

Integration records expected old HEAD, candidate commit and an intent before compare-and-swap ref update. A crash after Git update is reconciled against recorded intent, rather than pretending SQLite and Git are atomic. An unexpected base change rejects integration and forces fresh validation; no silent merging. All integration is local, with no remote publication. The fixed supervisor cannot modify its own source during unattended jobs. Independent clones and reviewer roles remain same-user cooperative auditability, not a hostile-worker security boundary.

CAS recovery may finalize only an index and working tree that exactly equal either persisted expected old Git tree or candidate tree, with no extra untracked files. A mixed tree or user modification enters conflict without reset. Before independent review, an old regular verdict is removed; symlinks and other nonregular paths are rejected. Only a newly generated regular verdict from the current call, bound by content hash and candidate identity, is eligible.

Canonical expected controller, config, generated CLI and Engine policy-body hashes live in coordinator SQLite outside the worker-writable attempt slot. A slot-side hash file is informational and cannot authorize drift. Trusted Python check scripts and sibling Python helper sources (including common.py) are fingerprinted; dynamic helper packages are outside this first contract. `--max-tasks` is a cumulative successful-job target for the runtime state, so recovery preserves its stopping point.

Before reserving any worker backend invocation (including a retry), the coordinator requires at least two remaining backend sessions: one worker and one independent reviewer. A reviewer may consume the final session. Rejected reservations leave spent calls, reservation totals and events unchanged; this gate never replenishes or enlarges the persisted budget. The local regression for this planning guard is a native maintenance repair, not an additional successful unattended task.

## Qualified retry source and admission

Failure rollback still archives the candidate. Before rollback, the coordinator can additionally qualify a source-only binary patch against the exact baseline HEAD/content, allowlist, canonical controller/config/Engine-policy hashes and trusted checker identities. The patch SHA and restored-source SHA live in coordinator SQLite outside worker-write grants. Modified tests/control/policy, a changed base, oversized/empty patches and symlinks are rejected. A runner-created recorded candidate commit can be exported after reviewer rejection; arbitrary worker commits cannot. A new attempt uses a fresh clone and fresh core state. Its worker must directly claim/progress and generate its own exact-baseline failed verification before explicitly invoking `jobctl restore`. Restore validates active fencing ownership before writing, checks base and patch/source identities, and emits progress. No old run/token, machine acceptance evidence or reviewer verdict is imported; the worker must submit the restored/revised source and all machine tests and independent review run again.

Retry feedback is typed inert JSON: previous failure stage/attempt, reviewer candidate/reason, command exit/timeout, machine-log reference and saved-log SHA, stream SHA, truncation and bounded retained-log excerpts. Excerpts from a truncated stream are the tail of the saved prefix, not the final output. The serialized context remains at most 16 KiB and excludes tokens/private arguments. Worker instructions name the timebox and one small checker goal, and direct the worker to restore qualified source and test it before adding more code.

Admission occurs before attempt increment, clone or core-task creation. It requires a worker/reviewer pair and sufficient original wall time for both configured backend caps plus hard machine windows. Test/verification/discovery calls are capped at `min(call_seconds,60)` seconds; administrative subprocesses at `min(call_seconds,10)`. The post-worker admission window is `2*call_seconds + (len(tests)+2)*min(call_seconds,60) + 4*min(call_seconds,10)`. Local Git/filesystem work is additional overhead; the total clock is rechecked at every supervised launch, so the window is not a guarantee that an AI succeeds. Insufficient admission produces `budget_blocked` and exits without consuming an attempt or starting a backend. The persistent live pilot budgets are unchanged; any future profile requires fresh authorization.

A check may opt into `finding_contract: "strict-v1"`. A formal finding requires exit 1 and a JSON object with matching `id` and `exactsourceSHA`, `source_stable:true`, `passed:false`, `classification:"product_defect"` and a list `evidence`. Exit 2, setup/traceback output, unstable source, timeout, truncated or invalid output is logged as infrastructure and creates no task. The default `legacy-v1` remains compatible with the original two checks but requires matching ID plus structured evidence and repair text; arbitrary nonzero process exit is not a product finding. The new behavior and reuse lifecycle were tested with local fixtures only, using zero additional external Codex invocations. Original pilot completion remains 1/2.

Feedback sanitization recursively handles complete log JSON objects, lists and embedded JSON strings before excerpt clipping. Token-bearing fragments that cannot be parsed (including truncated escaped records) are conservatively replaced instead of quoted. Long token values cannot leak by slicing away their key. This only changes feedback copies; protected raw logs and their recorded SHA identities remain unchanged. The nested-token regression uses a fake sentinel and native subprocess fixtures, with no actual credential or external API call.

## Receipt and summary commands

`receipt.py` adapts only exec-v1 events. Known completion is an observation, not acceptance. Controller `completion_receipt(job)` reads canonical current job/run/control identity, actual machine log hashes, reviewer verdict file/hash, executed backend content version and CAS/main HEAD/source. Normal completion and after-CAS recovery both require this collector. Unsupported/missing evidence blocks the completion; old no-context integration fixtures are explicitly `legacy_integration_unverified`, never a new trusted receipt. Receipts are stored outside source under `receipts/<job>.json`; their full manifest must be complete.

`python3 -m agent_workflow.metrics --state ABS` opens only existing SQLite with `mode=ro`; it does not instantiate Runner, migrate schema, clear stop or rewrite a launcher. Default parent goals come from frozen configuration checks, not the number of jobs/attempts. `calls` counts backend worker/reviewer sessions; local reservations, timeout observations, absent usage and historical completed jobs are separate fields. Cost and intervention counts are unknown. Legacy completions without receipts remain historical claims with unknown current receipt verification. Optional `--cohort FILE --events FILE` evaluates the fixed pure JSON contract, rejecting conflicting duplicates or unregistered child goals.

SO001/002/003 checks use trusted immutable native fixtures and whole-unit verification. The internal workers really claimed/submitted via frozen CLI, but these fixtures and four historical exec replays do not constitute newly executed external agents. The original first pilot's 1/2 result and the separate later 2/2 historical batch are retained as separate facts; no old receipt, source version or budget was retroactively rewritten.
